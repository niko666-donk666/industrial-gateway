## USART2 中断与环形缓冲区：第一组

1. `App_Init()` 中的 `HAL_UART_Receive_IT()` 让 USART2 一次接收几个字节？接收到的字节先保存在哪里？
2. `HAL_UART_RxCpltCallback()` 的末尾为什么必须再次调用 `HAL_UART_Receive_IT()`？
3. 环形缓冲区的写入下标 `head` 和读取下标 `tail` 分别由谁推进？两者相等代表什么？
4. 当 `head` 的下一个写入位置等于 `tail` 时代表什么？当前代码怎样处理这个新字节？

### 参考答案

1. 一次接收一个字节。HAL先把字节保存到全局单字节临时变量 `s_esp_rx_irq_byte`，接收完成回调再把它复制到环形缓冲区。
2. 本次配置的异步接收长度只有一个字节，完成后需要重新调用该函数，为下一个字节重新挂起接收；这不是重新初始化整个串口。
3. `head`由USART2接收完成回调推进，`tail`由通信任务调用的 `EspRxPop()`推进；两者相等表示环形缓冲区为空。
4. 这表示环形缓冲区已满。当前代码不保存这个新字节、不推进 `head`，但仍会重新挂起下一字节接收。

## USART2 中断与环形缓冲区：第二组

1. `s_esp_rx_ring` 和 `link.rx_line` 分别解决什么问题？
2. `while (EspRxPop(&byte))` 什么时候结束？结束是否意味着 USART2 以后不能再接收？
3. 收到 `\n` 后，为什么必须在行缓冲区末尾补上 `\0`？
4. 报文成功解析出序号以后，为什么还不能立即认定为有效 ACK？还要检查哪两个条件？

### 参考答案

1. `s_esp_rx_ring`用于暂存中断收到的原始字节，解决中断向任务交付数据的问题；`link.rx_line`用于把这些字节拼成一行完整协议帧。
2. 环形缓冲区暂时为空、`EspRxPop()`返回0时结束。它只表示当前数据已取完，USART2中断以后仍可继续接收新字节。
3. `\0`是C字符串结束符，`sscanf()`等字符串函数依靠它判断字符串在哪里结束；它不是UART接收到的字节。
4. 还要检查 `waiting_ack`为真，并且解析出的序号等于 `pending_seq`。加上格式解析成功，一共是三个有效ACK条件。

## 有效 ACK 的状态更新

1. `ack_seen` 和 `waiting_ack` 都与 ACK 有关，它们有什么本质区别？
2. 为什么判断 ESP32 在线时，不能只使用 `now - last_ack_tick < 3000 ms`？
3. 有效 ACK 到达并使 `waiting_ack = 0` 后，500 ms 超时检查还会不会触发重传？为什么？
4. 为什么修改共享状态中的 `ack_count` 需要互斥锁，而修改 `LinkContext` 中的 `last_ack_tick` 通常不需要？

### 参考答案

1. `ack_seen`是历史标志，表示系统启动后是否至少收到过一次有效ACK；`waiting_ack`是当前状态，表示STM32是否正在等待本轮心跳的ACK。
2. `LinkContext`启动时被清零。如果只判断时间，刚启动时可能出现 `now - 0 < 3000 ms`，从而在尚未收到任何ACK时错误判断ESP32在线，因此还必须要求 `ack_seen == 1`。
3. 不会。超时重传条件首先要求 `waiting_ack`为真，有效ACK将它清零后，该条件不再成立。
4. `ack_count`位于多个任务可能读写的共享状态 `s_status`中，需要互斥保护；`last_ack_tick`位于通信任务私有的 `LinkContext`中，通常只有该任务访问。

## ACK 超时与重传状态机

1. 初次发送是否计算在 `retry_count` 允许的 3 次重传以内？
2. 为什么每次重传以后都要刷新 `last_tx_tick`？
3. 假设 0 ms 初次发送序号 12，并且一直没有收到 ACK，那么 500、1000、1500 和 2000 ms 分别发生什么？
4. 已经达到重传上限、`waiting_ack` 变为 0 后，序号 12 的迟到 ACK 为什么不会被接受？

### 参考答案

1. 初次发送不算重传，初次发送时 `retry_count = 0`；随后最多重传3次，因此最多实际发送4次。
2. `last_tx_tick`记录最近一次发送时刻。重传后刷新它，可让下一次500 ms超时从本次重传重新开始计算。
3. 500 ms第一次重传，1000 ms第二次重传，1500 ms第三次重传；2000 ms达到上限，结束本轮等待并使 `timeout_count`加一。约2500 ms才满足下一轮心跳周期并产生新序号。
4. 新一轮开始前，`waiting_ack == 0`已经足以拒绝迟到ACK；新一轮开始后，新的 `pending_seq`也不再是12，因此序号仍不匹配。

## UART 接收异常边界

1. UART ORE、环形缓冲区写满、`rx_line` 写满分别发生在哪一层？
2. 环形缓冲区写满时，当前代码怎样处理新字节？为什么可能使一整帧失效？
3. `rx_line` 写满以后只设置 `rx_length = 0`，为什么还不够安全？
4. 当前 `HAL_UART_ErrorCallback()` 完成了什么？还缺少哪些恢复信息或处理？

### 参考答案

1. ORE发生在USART硬件接收层；环形缓冲区写满发生在中断与任务之间的软件缓冲层；`rx_line`写满发生在通信任务的协议拼帧层。
2. 当前代码静默丢弃新字节，但继续接收后续字节。丢失的可能是格式字符、序号数字或换行符，因此可能破坏整帧。
3. 清零后，超长异常帧并没有真正结束，剩余部分还会被当成新帧继续接收，甚至可能碰巧组成看似合法的ACK。
4. 当前错误回调判断USART2、清除ORE并重新挂起下一字节接收。它还缺少错误计数、当前帧损坏标志、丢弃到下一个换行符的重新同步处理，以及重新挂起失败后的统计和恢复。

合理升级方案是：分别增加UART错误、环形缓冲区溢出和行缓冲区溢出计数；发生丢字节或行溢出后进入“丢弃直到下一个 `\n`”状态，收到换行符后再从下一帧重新开始。还可使用任务通知及时唤醒通信任务；持续高吞吐时再升级为DMA循环接收加IDLE检测。

## ESP32 接收心跳并回复 ACK

1. `uart_read_bytes()`一次返回的数据是否一定是一整帧？可能出现哪些情况？
2. ESP-IDF 内部接收缓冲区、`data` 数组和 `line` 数组分别有什么作用？数据按照什么顺序在它们之间流动？
3. `GatewayUartTask()`收到普通字符、`\r`和`\n`时分别怎样处理？
4. ESP32 为什么不能自己生成新的 ACK 序号，而必须使用 STM32 心跳中的原序号？

### 参考答案

1. 不一定。它可能返回0字节、半帧、一整帧或一次包含多帧的数据块，因为UART提供的是连续字节流。
2. ESP-IDF内部接收缓冲区保存尚未被任务读取的UART字节；`data`保存本次 `uart_read_bytes()`批量取出的数据；`line`跨多次读取拼接一帧完整文本。数据顺序为：UART硬件→驱动内部缓冲区→`data`→`line`→`ProcessLine()`。
3. 普通字符从 `data`追加到 `line`；`\r`被忽略；`\n`表示一帧结束，程序给 `line`补 `\0`，调用 `ProcessLine()`，再把 `line_length`清零。
4. ACK需要与某一轮心跳对应。ESP32复制原序号后，STM32才能与 `pending_seq`比较并拒绝旧ACK；同一心跳重传时，ESP32也应继续回复相同序号。

## Modbus、Wi-Fi 与 MQTT 基础

1. RS-485 和 Modbus 有什么区别？
2. ESP32 连接上 Wi-Fi，是否代表 MQTT 也一定连接成功？为什么？
3. MQTT 中的 Broker 和 Topic 分别是什么？
4. 请按照顺序说出“Modbus 从机数据最终到达 MQTTX”的完整链路。

### 参考答案

1. RS-485是差分电气传输标准，规定信号怎样通过A/B线传输；Modbus是工业主从通信协议，规定地址、功能码、寄存器、数据和CRC等问答格式。
2. 不代表。获得Wi-Fi IP只说明ESP32具备网络通信条件；MQTT客户端还要根据Broker的IP或域名建立TCP连接并完成MQTT连接。
3. Broker是接收并转发MQTT消息的中转服务器；Topic是消息的分类名称或频道，不是订阅者的IP地址。订阅者主动连接Broker并订阅Topic。
4. Modbus从站保存寄存器数据→STM32主站通过USART1、MAX3485和RS-485发送读取请求→从站应答→STM32检查地址、功能码、长度和CRC并保存数据→STM32通过USART2自定义文本协议发送给ESP32→ESP32解析并转换为JSON→通过Wi-Fi/IP连接MQTT Broker并发布到Modbus Topic→MQTTX连接同一个Broker并订阅该Topic→Broker把消息转发给MQTTX。

## ESP32 Wi-Fi事件与状态管理

1. 为什么 `esp_wifi_start()` 返回成功，也不能说明 ESP32 已经获得网络连接？
2. `WIFI_EVENT_STA_START`、`WIFI_EVENT_STA_DISCONNECTED` 和 `IP_EVENT_STA_GOT_IP` 分别表示什么？程序分别怎样处理？
3. Wi-Fi断开时，为什么要同时清除 `WIFI_CONNECTED_BIT` 和 `MQTT_CONNECTED_BIT`？
4. 为什么项目使用两个事件位，而不是只使用一个 `network_online` 变量？

### 参考答案

1. 返回成功只表示Wi-Fi驱动已经成功启动，后续的SSID连接、密码认证和DHCP获取IP仍是异步过程。收到 `IP_EVENT_STA_GOT_IP`后，才说明ESP32具备IP网络通信能力。
2. `WIFI_EVENT_STA_START`表示STA模式的Wi-Fi驱动已经启动，程序调用 `esp_wifi_connect()`开始连接；`WIFI_EVENT_STA_DISCONNECTED`表示ESP32与接入点断开，程序清除Wi-Fi和MQTT状态位并重新连接；`IP_EVENT_STA_GOT_IP`表示ESP32已经获得IP地址，程序设置 `WIFI_CONNECTED_BIT`。
3. ESP32的MQTT客户端通过Wi-Fi/IP建立与Broker之间的TCP连接。Wi-Fi断开后，这条网络基础链路失效，因此当前MQTT连接也不能继续视为可用。该状态位与MQTTX是否在线无关。
4. 两个位分别表示ESP32是否已经获得Wi-Fi IP，以及ESP32的MQTT客户端是否已经连接Broker。分开记录可以区分“无线网络未就绪”和“Wi-Fi正常但Broker连接失败”；一个总变量无法准确定位故障层。

## ESP32 MQTT连接事件与遗嘱消息

1. 为什么 `esp_mqtt_client_start()` 返回成功，仍然不能把 `MQTT_CONNECTED_BIT` 设置为1？
2. 收到 `MQTT_EVENT_CONNECTED` 后，当前项目主要完成哪三件事？
3. Broker连接断开时，为什么通常只清除 `MQTT_CONNECTED_BIT`，而不一定清除 `WIFI_CONNECTED_BIT`？
4. MQTT遗嘱消息解决了什么问题？为什么项目把 `offline` 设置为保留消息？

### 参考答案

1. `esp_mqtt_client_init()`负责根据配置创建客户端对象；`esp_mqtt_client_start()`返回成功只表示MQTT客户端后台任务已经启动并开始尝试连接。TCP连接、MQTT CONNECT和Broker认证仍是异步过程，只有收到 `MQTT_EVENT_CONNECTED`后才能设置连接位。
2. 第一，设置 `MQTT_CONNECTED_BIT`；第二，向状态Topic发布QoS 1、retain为1的 `online`消息；第三，设置 `s_publish_latest = true`，要求任务随后重新发布最近一份遥测和Modbus记录。消息发布目标是Broker，不是直接上传到MQTTX。
3. Broker或MQTT连接可能单独故障，而ESP32仍然连接Wi-Fi并持有有效IP。因此只清除MQTT位，可保留“Wi-Fi正常但MQTT失败”的真实状态；如果Wi-Fi断开，Wi-Fi事件处理函数会同时清除两个位。
4. ESP32突然断电或网络异常时，可能来不及主动发布离线消息。Broker检测到客户端异常失联后，会按照预先配置的Last Will代替设备发布 `offline`。设置retain后，Broker保存最近的在线/离线状态，后来连接的订阅者也能立即看到设备最后状态。

## JSON生成、MQTT发布与QoS

1. 为什么 `PublishTelemetry()` 必须同时检查 `valid` 和 `MqttConnected()`？
2. `root` 和 `json` 分别是什么？为什么发布后必须调用 `cJSON_free()` 和 `cJSON_Delete()`？
3. `esp_mqtt_client_publish()` 返回有效 `message_id`，是否证明MQTTX已经收到消息？为什么？
4. QoS 1和 `retain = 1` 分别解决什么问题？为什么遥测使用 `retain = 0`，而在线状态使用 `retain = 1`？

### 参考答案

1. `valid`表示ESP32已经收到并成功解析过一帧真实遥测，避免刚启动或尚无数据时发布默认全零记录；`MqttConnected()`表示ESP32的MQTT客户端已经连接Broker，只有满足两者才有有效内容和可用发布链路。
2. `root`是指向堆内存中cJSON对象树根节点的指针；`json`是 `cJSON_PrintUnformatted()`另外动态生成的连续JSON文本。`cJSON_Delete(root)`释放整棵对象树，`cJSON_free(json)`释放序列化字符串，否则周期发布会造成堆内存泄漏。
3. 不能。有效 `message_id`表示MQTT客户端已为事务编号并成功发送或排队，但不表示Broker已返回确认，更不表示MQTTX已收到。对于QoS 1，收到相同ID对应的 `MQTT_EVENT_PUBLISHED`才表示Broker的PUBACK已到达；要确认订阅端完成业务处理，还需要应用层确认。
4. QoS 1保证发布者到Broker这一段“至少一次”，因此消息可能重复。retain让Broker为某个Topic保存最近一条消息。普通遥测使用retain 0，避免把Broker当作历史数据库或让新订阅者先看到一条可能已经过时的数据；历史数据应由后端数据库保存。状态消息使用retain 1，使后来订阅的客户端立即得到设备最近的 `online`或 `offline`状态。

这里的 `online`表示ESP32的MQTT客户端已经连接Broker，即设备的网络/MQTT连接在线；`offline`通常由Broker在设备异常失联时根据Last Will发布。它不表示MQTTX在线，也不能证明STM32、传感器、Modbus和全部业务功能都正常。

## Modbus RTU请求、收发切换与响应校验

1. 请求帧 `01 03 00 00 00 02 C4 0B` 中，每一部分分别表示什么？
2. 为什么发送前要让DE进入发送模式，发送完又必须马上切回接收模式？
3. 读取两个寄存器时，正常响应为什么有4字节数据、总共9字节？
4. STM32至少检查响应中的哪些内容，才能认为这是一次有效的Modbus回复？

### 参考答案

1. `01`是从机地址；`03`是读取保持寄存器功能码；`00 00`是起始寄存器地址；`00 02`表示连续读取2个寄存器；`C4 0B`是对前6字节计算出的Modbus CRC，发送顺序为CRC低字节在前、高字节在后。`00 02`表示读取数量，不是寄存器的数据内容。
2. 当前MAX3485链路采用半双工通信，同一对A/B线分时发送和接收。发送前置位DE，让收发器驱动总线；UART确认请求发送完成后要立即撤销DE、进入接收模式，因为从机可能很快开始应答。若切换过晚，STM32可能漏掉响应开头；若始终处于发送状态，还可能继续占用总线并与从机发送发生冲突。
3. 一个Modbus寄存器是16位，即2字节；两个寄存器的数据区因此是4字节。正常响应由从机地址1字节、功能码1字节、数据字节数1字节、寄存器数据4字节和CRC 2字节组成，所以总长度为 `1 + 1 + 1 + 4 + 2 = 9` 字节。
4. 当前项目检查UART是否在规定时间内接收成功、从机地址是否匹配、功能码是否为正常的 `0x03` 或对应异常功能码 `0x83`、数据字节数是否等于寄存器数量乘2，以及整帧CRC是否正确。正常响应全部通过后才解析寄存器并设置 `online = true`；异常响应会读取异常码，但仍把本次访问判为失败。发送请求本身也有超时检查，但它属于请求能否成功发出，不是对响应内容合法性的判断。

## Modbus RTU正常响应与异常响应

1. 功能码 `0x83` 和 `0x03` 是什么关系？为什么不能把 `0x83` 当成正常数据？
2. 正常响应和异常响应中的第三个字节，含义分别是什么？
3. 如果STM32请求一个不存在的寄存器，从机返回异常码 `02`，这说明RS-485通信完全失败了吗？
4. 为什么代码先接收3字节，再根据前三字节决定后续接收长度，而不是一开始固定接收最大长度？

### 参考答案

1. `0x83`等于正常功能码 `0x03` 的最高位置1，即 `0x03 | 0x80`，表示从机收到了请求但无法正常执行。它后面携带的是异常码，不是寄存器数据，因此不能按正常响应解析。
2. 正常 `0x03` 响应的第三字节表示后续寄存器数据占多少字节；异常 `0x83` 响应的第三字节表示异常原因，例如 `01`为非法功能、`02`为非法数据地址、`03`为非法数据值、`04`为从机设备故障。
3. 不说明物理通信完全失败。能够收到地址、异常功能码、异常码且CRC正确的响应，反而说明UART、MAX3485、A/B总线及基本Modbus问答已经工作；问题位于应用配置层，通常是起始寄存器或数量不符合从机寄存器表。
4. 收到前三字节后，程序才能根据功能码区分正常响应与异常响应，并根据正常响应的字节数字段计算实际总长度。这样只读取本帧应有的字节，避免为了等待不存在的“最大长度剩余字节”而超时，也避免把下一帧数据误当成本帧尾部。

## FreeRTOS共享状态、快照与互斥锁

1. `sample`、`s_status`和`snapshot`分别是什么，谁负责写、谁负责读？
2. 为什么不能只给写入`s_status`的一方加锁，而读取方完全不加锁？
3. 为什么OLED刷新和Modbus串口等待不能放在`s_status_mutex`保护范围内？
4. `s_status_mutex`和`s_i2c_mutex`分别保护什么？为什么不应该把它们合成一把锁？

### 参考答案

1. `sample`是生产数据任务的局部样本，例如`ModbusTask`把一次读取的结果保存在自己的`ModbusData sample`中，`SensorTask`也使用自己的`SensorData sample`；样本准备完整后，任务短时间持锁并把它复制到全局共享状态`s_status`。`s_status`是多个任务共同访问的网关总状态，由传感器、Modbus和通信任务分别更新相应成员。`snapshot`是读取任务在锁内从`s_status`复制出的私有快照，`DisplayTask`用它刷新OLED，`CommunicationTask`用它生成发往ESP32的遥测和Modbus报文。
2. 结构体复制由多次内存访问组成。即使写入方持锁，如果读取方不获取同一把锁，它仍可能在写入进行到一半时读取，从而得到一部分新字段和一部分旧字段。读写双方都遵守同一把锁，才能保证读取的是更新前或更新后的完整状态。
3. OLED的I²C刷新和Modbus串口等待都可能耗费较长时间。若在这些操作期间一直持有状态锁，其他需要读取或更新`s_status`的任务会被无关的慢速操作长期阻塞。正确做法是先在锁外完成采集，或在锁内快速复制快照，然后立即解锁，再在锁外执行慢速外设操作。
4. `s_status_mutex`保护`s_status`结构体的数据一致性；`s_i2c_mutex`保护I2C1硬件总线，防止传感器任务与OLED显示任务的I2C事务互相穿插。技术上可以用一把大锁保护所有资源，但这会把互不相关的状态访问和I2C访问错误耦合，扩大临界区、增加无关阻塞，并提高后续产生锁顺序问题的风险，因此应按独立资源分别加锁。

## 软件任务健康监控与硬件IWDG

1. 为什么`s_task_health[]`保存的是时间戳，而不是简单的`true/false`？
2. Modbus从机断线，导致每次读取都失败，但`ModbusTask`仍正常执行错误处理。这个任务算健康吗？
3. 为什么不能让COMM、SENSOR等任务各自直接调用`HAL_IWDG_Refresh()`？
4. 某任务超过健康期限以后，STM32是立刻复位，还是还要经过另一个过程？完整过程是什么？

### 参考答案

1. 时间戳记录任务最近一次运行到健康标记位置的时刻，监督任务可以用“当前时刻减去最近健康时刻”判断它是否长期没有进展。简单布尔值一旦被设置为真，即使任务后来卡死也可能一直保持真，无法反映健康信息是否已经过期。
2. 算健康。Modbus从机离线属于外部设备或通信结果失败；只要`ModbusTask`能够在UART等待结束后完成错误统计、调用`TaskHealthMark()`并进入下一轮调度，它自身仍在正常运行。需要区分“某次Modbus通信超时”和“Modbus任务长时间没有上报健康”。
3. 当前所有任务面对的是同一个IWDG倒计时器。若各任务都有权刷新，只要还有任意一个正常任务持续喂狗，IWDG就不会超时，其他已经卡死的任务会被掩盖。项目让业务任务只上报健康时间，由集中监督任务确认全部任务健康后统一刷新IWDG。
4. 不会立即复位。监督任务发现任一任务超过期限后，把`all_healthy`判为假并停止调用`HAL_IWDG_Refresh()`；IWDG从最近一次刷新后继续按照独立硬件时钟倒计时，计数耗尽才复位整个STM32。复位后程序重新从复位入口、`main()`、外设初始化、任务创建和调度器启动开始运行。当前典型配置的IWDG超时时间约为8秒，但LSI频率有误差，所以实际时间并非严格8.000秒。

## I2C传感器、定点数据与OLED降级显示

1. AHT20、INA219和SSD1306为什么可以同时连接I2C1，而不会不知道数据发给谁？
2. `temperature_deci_c = 253`、`humidity_deci_percent = 618`分别表示多少？为什么不用浮点数直接保存？
3. SensorTask为什么先释放`s_i2c_mutex`，再获取`s_status_mutex`，而不是同时拿着两把锁？
4. AHT20缺失时，项目会不会因此停止心跳、Modbus和OLED任务？OLED如何表示缺失？

### 参考答案

1. 三个设备可以同时物理连接在I2C1的SCL和SDA线上，因为它们使用不同的七位地址：AHT20为`0x38`、INA219为`0x40`、SSD1306为`0x3C`。STM32作为主机，在一次事务开始时发送目标地址，只有匹配地址的从机应答。它们不能在同一时刻各自独立占用总线通信，但可以共享同一条总线并由主机依次访问。
2. `253`表示25.3℃，`618`表示61.8%RH。项目使用“整数值加明确单位”的定点表示，避免STM32F103在没有硬件浮点单元时承担较重的浮点运算和格式化开销，也便于UART文本协议传输，并使精度和单位明确。
3. SensorTask先单独持有I2C锁完成慢速外设读取，把结果准备在私有`sample`中，释放I2C锁后才短时间持有状态锁发布样本。这样缩短了各自的临界区，不会让只想读取`s_status`的任务因为I2C等待而阻塞；同时避免两把锁嵌套，降低不同任务采用相反加锁顺序时发生死锁的风险。
4. 不会停止其他任务。如果AHT20在初始化时没有应答，`s_aht20_ready`保持为假，后续`Sensors_Read()`不会继续执行AHT20读事务，只会把本次样本的`aht20_ready`设置为假。SensorTask本身仍周期运行并发布降级状态，心跳、Modbus和OLED任务继续调度；DisplayTask显示`T:--.-C H:--.-`。当前代码不会自动重新探测启动时缺失的传感器，这是一个可升级边界。

## 传感器原始数据到工程量的换算

1. 为什么AHT20换算公式中会出现`1048576`？湿度原始值等于`524288`时表示多少？
2. 温度公式最后为什么减去`500`？它在当前数据单位下代表什么？
3. INA219母线电压数据右移后等于1250，项目最终得到多少mV和多少V？
4. INA219的`raw_shunt`为什么使用`int16_t`而不是`uint16_t`？负电流通常表示什么？

### 参考答案

1. AHT20的湿度原始数据是20位，完整比例分母为`2^20 = 1048576`。原始值`524288`正好是满量程的一半，换算后保存为`500`个0.1%，即50.0%RH。
2. AHT20温度范围公式包含`-50℃`偏移。项目以0.1℃为单位保存，所以`-50.0℃`写成`-500`；它不是减去500℃。完整定点公式等价于`raw / 2^20 × 2000 - 500`。
3. 每个有效母线电压单位表示4mV，因此`1250 × 4 = 5000mV`，即5.000V。右移3位是为了丢弃INA219母线电压寄存器中不属于电压数值的状态位。
4. INA219的分流电压和由其计算的电流具有方向，可能为正也可能为负，因此必须使用有符号16位数。负电流通常表示实际电流方向与项目定义的正方向相反，不一定表示测量错误。

## SSD1306显存、字库与降级运行

1. 为什么调用`SSD1306_Clear()`后，实体屏幕可能仍显示旧内容？
2. 128×64像素的屏幕为什么只需要1024字节缓冲区？
3. `SSD1306_WriteString()`是直接把ASCII字符串交给OLED吗？它实际做了什么？
4. OLED初始化失败后，DisplayTask是否算卡死？软件看门狗会不会因此复位系统？

### 参考答案

1. `SSD1306_Clear()`只用`memset()`清空STM32 RAM里的`s_buffer`，尚未改变SSD1306内部显存。只有随后调用`SSD1306_Update()`，把新缓冲内容通过I2C发送给屏幕，实体画面才会清空。
2. 屏幕共有`128 × 64 = 8192`个单色像素，每个像素只需要1位；一个字节有8位，因此需要`8192 ÷ 8 = 1024`字节。SSD1306还把垂直8个像素组织为一个字节，形成8页、每页128字节，即`8 × 128 = 1024`字节。
3. 不是。SSD1306本身不理解ASCII字符的外形。`SSD1306_WriteString()`逐字符在项目的5×7点阵字库中查找字形，把每个字符的5列像素和1列间隔写入RAM缓冲区；`SSD1306_Update()`随后才把像素数据发送给屏幕。不受字库支持的字符会使用空格字形。
4. 不算卡死，也不会仅因OLED缺失触发看门狗复位。初始化失败后`s_ready`为假，DisplayTask跳过清屏、写字和I2C刷新，但仍执行`TaskHealthMark(HEALTH_DISPLAY)`并按500 ms周期继续运行。这里应区分“显示设备不可用”和“显示任务失去调度或永久阻塞”。

## STM32启动流程、降级运行与致命错误

1. `xTaskCreate()`成功以后，任务为什么还不一定立即执行？什么时候才开始由FreeRTOS调度？
2. AHT20初始化失败和`s_status_mutex`创建失败，为什么项目对它们采取不同处理？
3. `vTaskStartScheduler()`正常情况下为什么不应该返回？如果返回，当前代码会怎样？
4. 当前项目在“任务创建失败”这个启动故障上，为什么可能无法依靠IWDG自动恢复？

### 参考答案

1. 调用`xTaskCreate()`只创建任务控制块、任务栈等内核对象，并把任务放入可调度状态；当前仍在启动调度器之前的单线程初始化阶段。调用`vTaskStartScheduler()`成功后，FreeRTOS才开始根据任务优先级和就绪/阻塞状态调度任务。
2. AHT20是可选业务外设，初始化失败只会使温湿度数据不可用，SensorTask仍可发布`ready=false`，其他任务继续降级运行。`s_status_mutex`是多个任务安全读写网关共享状态的基础同步资源；创建失败后继续运行会破坏并发访问前提，因此当前项目将其视为无法安全启动的致命错误并进入`Error_Handler()`。
3. 调度器启动成功后，CPU会一直在就绪任务、阻塞任务和Idle任务之间切换，任务函数本身也采用无限循环，因此控制流不应回到`vTaskStartScheduler()`的下一行。若它返回，通常表示调度器启动失败；当前`App_StartScheduler()`随即调用`Error_Handler()`，关闭中断并进入无限循环。
4. `App_Init()`先创建全部任务，成功后才调用`WatchdogInit()`。如果某次`xTaskCreate()`失败，代码会在IWDG初始化之前进入`Error_Handler()`；该函数关闭中断并永久循环，而硬件IWDG尚未开始倒计时，所以无法依靠它自动复位恢复。这是当前启动错误处理的设计边界。
