# v0.7 看门狗与安全浅睡眠设计及实验流程

## 1. 本版本目标

在不破坏STM32与ESP32串口心跳、OLED刷新、传感器轮询、Modbus以及Wi-Fi/MQTT在线状态的前提下，增加：

1. STM32任务级健康监督与独立看门狗复位；
2. ESP32任务看门狗与复位原因日志；
3. STM32空闲态浅睡眠；
4. ESP32保持网络连接的Wi-Fi省电模式。

本版本不启用STM32 STOP/Standby，也不启用ESP32 Light-sleep/Deep-sleep。这是一个优先保证通信可靠性的保守方案。

## 2. STM32设计

### 2.1 任务健康监督

新增高优先级`SUPERVISOR`任务，每500 ms检查各业务任务最近一次完成循环的时间：

| 任务 | 最大允许无更新时长 | 说明 |
|---|---:|---|
| `COMM` | 1000 ms | 心跳、ACK和重传必须保持快速响应 |
| `SENSOR` | 5000 ms | 覆盖I2C测量等待和2秒采样周期 |
| `DISPLAY` | 2000 ms | 覆盖OLED刷新耗时和500 ms刷新周期 |
| `MODBUS` | 4000 ms | 覆盖串口响应超时和2秒轮询周期 |

每个任务只有在本轮工作完成后才更新自己的健康时间。`SUPERVISOR`只有确认四个任务全部健康时才刷新独立看门狗，因此某个任务永久阻塞时不会被其他正常任务掩盖。

### 2.2 独立看门狗 IWDG

- 时钟源：STM32内部LSI；
- 预分频：256；
- 重装值：1249；
- 按40 kHz典型LSI估算，超时约8秒。

LSI频率存在器件和温度偏差，因此8秒是设计估算值，不是精密计时值。任务监督阈值均明显短于IWDG超时，留出了调度和外设短暂阻塞余量。

启动时读取并清除RCC复位标志。若上一次由IWDG复位，OLED统计行显示`W:R`；否则显示`W:-`。

### 2.3 STM32安全浅睡眠

FreeRTOS空闲钩子执行`__WFI()`：

- CPU在没有可运行任务时等待中断；
- SysTick、UART和其他中断均可立即唤醒CPU；
- 不设置`SLEEPDEEP`，不进入STOP或Standby；
- 外设时钟和RAM状态保持不变；
- 不改变现有FreeRTOS调度周期和串口协议。

由于当前仍有1 ms SysTick和周期任务，节能幅度预计有限，但方案风险低，适合作为第一阶段低功耗设计。

## 3. ESP32设计

### 3.1 任务看门狗

`GatewayUartTask`注册到ESP-IDF Task Watchdog，并在每轮UART处理及MQTT发布工作完成后复位计时器：

- 超时：10秒；
- 超时动作：启用panic并由系统复位；
- 启动日志：输出`Reset reason=<数值>`，用于追踪复位来源；
- ESP-IDF原有中断看门狗和两个Idle任务监视保持启用。

10秒阈值高于正常UART等待和MQTT发布耗时，可避免短暂网络抖动导致过于激进的复位，同时仍能恢复永久阻塞。

### 3.2 Wi-Fi安全省电

Wi-Fi启动后显式设置`WIFI_PS_MIN_MODEM`：

- 保持Station关联；
- 保持TCP及MQTT会话；
- 在无线空闲窗口关闭部分射频活动；
- 启动日志显示`Wi-Fi power save: MIN_MODEM`。

这里没有启用ESP32自动Light-sleep，因为当前ESP32需要持续处理STM32 UART心跳、MQTT连接和网络重连；直接进入更深睡眠可能增加延迟、丢失串口数据或造成MQTT离线。

## 5. 实机实验流程

### 5.1 烧录

1. 使用Keil将STM32工程下载到开发板；
2. 涉及ESP32时，默认在VS Code命令面板执行总命令：

```text
ESP-IDF: Build, Flash and Monitor your Device
```

只有总命令不可用时，才分别执行Build、Flash、Monitor。

### 5.2 正常运行回归

接线保持：

```text
STM32 PA2 -> ESP32 GPIO16
STM32 PA3 <- ESP32 GPIO17
STM32 GND -> ESP32 GND
两块板分别USB供电，不连接3.3V/5V
```

观察10至30分钟，记录：

1. OLED是否显示`NET: ESP ONLINE`；
2. `ACK`是否持续递增、`TO`是否无异常快速增长；
3. 正常启动时OLED是否显示`W:-`；
4. ESP32日志是否出现`Reset reason=`和`Wi-Fi power save: MIN_MODEM`；
5. 串口心跳/ACK、MQTT telemetry与modbus消息是否持续更新；
6. 是否出现无故复位、MQTT反复离线或UART丢帧。

### 5.3 STM32看门狗故障注入

该实验会故意让程序停止运行，只在受控桌面环境进行：

1. 保持两块板正常连接并确认OLED显示`W:-`；
2. 使用Keil调试器暂停STM32内核超过10秒；
3. 不要启用“调试暂停时冻结IWDG”的选项；
4. 退出暂停或重新连接调试器，观察STM32是否已自动复位；
5. 复位后的OLED应显示`W:R`，随后UART ACK应自动恢复递增。

若调试器自动冻结了IWDG，则此方法不能作为看门狗证据，应停止实验并改用后续专用故障注入固件，不要通过随意短接引脚制造故障。

### 5.4 ESP32看门狗验证

当前正式固件未保留人为卡死入口，避免误触发生产复位。现阶段先验证长期运行无误复位；后续如需严格故障注入，将另做默认关闭的测试构建，并记录任务看门狗复位日志。

### 5.5 低功耗验证

当前可以先做功能回归，确认省电设置没有破坏通信。定量功耗对比应等待INA219或万用表具备后再做：

1. 相同供电、相同Wi-Fi信号和相同MQTT上报周期；
2. 分别测量省电关闭与开启时的平均电流；
3. 每种状态至少记录5分钟；
4. 同时记录UART丢帧、MQTT断线次数和平均发布间隔。
