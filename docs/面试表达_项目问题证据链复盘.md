# 工业设备远程运维与故障诊断终端：面试表达与问题证据链复盘

## 使用说明

本文只整理项目中真实实施或真实验证过的内容，不把未验证的猜测包装成结论。面试时建议遵循：

> 现象 → 已知事实 → 假设 → 验证方法 → 结论 → 改进与复盘

不要把全文逐字背诵。先记住项目结构和三条问题链，再根据面试官追问展开。

## 一、60 秒项目介绍

我做的是一套基于 STM32、FreeRTOS 和 ESP32 的工业设备远程运维与故障诊断终端。STM32 负责实时侧的数据采集和现场通信，包括通过 I2C 读取 AHT20 温湿度与 INA219 电压、电流、功率，通过 Modbus RTU 读取 RS485 从站，并驱动 OLED 显示；ESP32 通过串口接收 STM32 数据，负责 Wi-Fi、MQTT 上云以及与 Qt 上位机的数据接口。

我把 STM32 和 ESP32 分开的原因是希望把实时采集、现场总线与网络连接解耦。即使 Wi-Fi 或 MQTT 暂时异常，STM32 的采集和 Modbus 轮询仍能继续运行。STM32 侧使用 FreeRTOS 拆分通信、传感器、Modbus 和显示任务，并加入任务健康监督与独立看门狗策略；双板串口协议带序号、ACK、超时和最多三次重传。

目前已经完成实机端到端验证：Qt 上位机能同时显示 AHT20 的温湿度、INA219 测得的风扇电压电流功率、Modbus 从站的两个保持寄存器，以及 STM32 与 ESP32 的心跳和 MQTT 发布状态。一次完整实验中，上位机显示温度 23.8 ℃、湿度 59.6 %RH、母线电压 4.91 V、电流 168 mA、功率 825 mW，Modbus 寄存器为 1234 和 5678，成功次数 82、错误次数 0。

## 二、最推荐主讲的问题：Modbus RTU 能请求但读不到响应

### 1. 面试口述版（约 2～3 分钟）

项目里最花时间的一次排障是 Modbus RTU 链路。STM32 是主站，电脑通过 USB 转 RS485 和 Modbus Slave 软件模拟 1 号从站。主站每秒用功能码 03 读取地址 0 开始的两个保持寄存器，测试值分别是 1234 和 5678。

最开始的现象比较容易误导：电脑端通信窗口能看到 STM32 发来的完整请求 `01 03 00 00 00 02 C4 0B`，也能看到电脑发出了包含 1234 和 5678 的 9 字节响应，但 STM32 的 OLED 显示 `MB RX:0/9 FAIL`、`NO RESPONSE E3`。也就是说，不能笼统地说“Modbus 不通”，因为请求方向已经通了，问题集中在响应返回链路。

我没有直接认定模块损坏，而是把链路拆成五段：电脑是否收到请求、模拟从站是否发出响应、RS485 A/B 物理链路是否正确、STM32 UART 是否收到字节、收到后地址、功能码、长度和 CRC 是否通过。为了把“没收到”和“收到但解析失败”区分开，我在 OLED 上增加了本轮接收字节数、前五个原始十六进制字节和错误码。`E3` 对应响应头等待超时，`B:0` 或 `0/9` 表示 UART 实际没有收到响应字节，所以当时不能把优先级放在 CRC 或寄存器解析上。

随后我按固定接线重新核对：STM32 PA9 接 RS485 模块 RXD，PA10 接 TXD，PB1 控制收发使能，模块使用 3.3 V，STM32、RS485 模块和 USB 转 RS485 共地，A 对 A、B 对 B；电脑从站统一配置为 9600、8N1、从站地址 1、功能码 03、起始地址 0、数量 2。同时保证发送完成后 PB1 及时切回接收方向，并排除串口被其他程序占用。

最终 OLED 显示 `MB RX:9/9 OK`，原始响应头为 `01 03 04 04 D2`，解析结果是 `R0:1234 R1:5678`；Qt 上位机显示 Modbus 在线、从站 1、异常码 0、成功 82、错误 0，电脑端请求和响应也保持每秒成对出现。这个问题让我认识到，电脑端“已经发送响应”并不等于 MCU “已经收到响应”，必须用每一层的证据逐段缩小范围。

### 2. 这段话体现的能力

- 会把“Modbus 不通”拆成方向明确、可以验证的链路。
- 能区分物理层未收字节与协议层解析失败。
- 会增加诊断信息，而不是只靠反复换线和重启。
- 不把“疑似模块损坏”说成已确认根因。
- 用电脑报文、OLED 原始字节和 Qt 最终数值形成闭环证据。

### 3. 证据表

| 阶段 | 观察结果 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 电脑收到请求 | `01 03 00 00 00 02 C4 0B` | STM32 发送、主站到电脑方向基本正常 | 不能证明响应能回到 STM32 |
| 电脑发出响应 | `01 03 04 04 D2 16 2E D5 46` | 模拟从站生成了正确响应 | 不能证明 STM32 UART 已收到 |
| OLED 失败阶段 | `MB RX:0/9 FAIL`、`E3` | 本轮等待响应头超时，实际收到 0 字节 | 不能据此直接判定模块损坏 |
| OLED 成功阶段 | `MB RX:9/9 OK`、`R0:1234 R1:5678` | STM32 已接收并通过协议校验、完成解析 | — |
| Qt 端到端结果 | 在线、成功 82、错误 0 | 数据已从从站经过 STM32、ESP32到达上位机 | — |

### 4. 如果面试官问“最终根因到底是什么”

建议这样回答：

> 当时不是靠一次测量锁定了某一个损坏器件，因此我不会说根因已经被证明是“模块坏了”。我能确认的是失败发生在从站响应到 STM32 UART 接收之间。通过统一共地、A/B、UART 引脚和 PB1 方向控制接线，并重新建立稳定连接后，9 字节响应能够持续收到。对学生样机来说已经完成了功能闭环；如果按产品故障分析标准继续做，我会用示波器或逻辑分析仪同时观察 A/B、RO/TXD 和 PA10，把最终物理故障点进一步定量确认。

这个回答比“换了模块就好了”更可信，因为它清楚区分了事实和推测。

## 三、第二个问题：MQTT 在 Wi-Fi 获得 IP 前启动

### 面试口述版（约 1～2 分钟）

ESP32 正式固件第一次启动时，串口先出现 `couldn't get hostname for broker.emqx.io`、MQTT transport connect 失败，几秒后才打印 Wi-Fi 获得 IP。表面看像网络不稳定，但我对照日志时间顺序后发现，问题不是 Broker 配置错误，而是程序时序错误。

原程序在 `app_main()` 里依次调用 Wi-Fi 初始化和 MQTT 初始化，但 Wi-Fi 初始化只是启动异步连接，并不会等 DHCP 和 DNS 就绪。程序紧接着启动 MQTT，因此第一次解析域名可能必然失败。

我把 MQTT 初始化改成只创建客户端和注册回调，在 `IP_EVENT_STA_GOT_IP` 事件到来后才启动 MQTT，并用状态标志防止重复启动。实机验证后的顺序变成：先提示等待 Wi-Fi IP，再获得 `192.168.3.123`，随后启动 MQTT，约 630 ms 后连接成功，启动阶段不再出现首次 DNS 和 transport 错误。

这个问题的复盘是：异步 API 调用成功不等于外部资源已经可用。相比简单延时，事件驱动能适应不同路由器和不同 DHCP 时延，状态也更明确。

### 面试官可能追问：为什么不用 `vTaskDelay(5000)`？

> 固定延时只能碰运气。网络可能 1 秒就绪，也可能超过 5 秒；延时过短仍失败，过长又浪费启动时间。`IP_EVENT_STA_GOT_IP` 是明确的状态证据，只有拿到有效 IP 后再启动 MQTT 才是稳定的依赖关系。

## 四、第三个问题：双板串口 ACK 超时与重传验证

### 面试口述版（约 1 分钟）

为了验证 STM32 与 ESP32 的串口协议不是只能在正常接线下工作，我做过一次主动断线实验。正常状态下，STM32 每秒发送带序号的心跳，ESP32返回相同序号的 ACK，序号持续递增。

我临时断开 ESP32 返回 ACK 的线路，也就是 STM32 PA3 到 ESP32 GPIO17 这条回传路径。ESP32 仍然能收到 STM32 心跳并打印已发送 ACK，但 STM32 实际收不到，所以同一个序号会每 500 ms 重发一次，表现为首次发送加最多三次重传。重新接回后，心跳恢复为每秒产生新序号。

这次实验说明我不仅实现了超时重传，还通过故障注入验证了发送方向正常、回传方向失败时状态机的行为。它验证的是协议机制，不依赖 LED 现象；LED 和 OLED 只作为辅助显示。

## 五、补充问题：移动工程后构建失败

### 简短口述版

我把 ESP32 工程从旧路径移动到新路径后，构建在生成链接脚本时提示找不到旧目录。我先搜索源码和配置，没有发现旧路径，后来在 `build/CMakeCache.txt` 找到大量旧绝对路径。说明问题来自生成缓存，不是源码。

处理时我保留源码和 `sdkconfig`，只把旧 build 目录改名备份，再让 ESP-IDF 在新路径重新生成构建目录，最终成功生成固件。复盘是 CMake 的 build 目录不是可移植源码，工程移动后应该重新配置，不能机械复制缓存。

## 六、五分钟完整回答模板

> 我做的是一套基于 STM32、FreeRTOS 和 ESP32 的工业设备远程运维与故障诊断终端。STM32 负责实时侧，通过 I2C 采集 AHT20、INA219并驱动OLED，通过 USART1 和 3.3 V RS485 模块作为 Modbus RTU 主站；ESP32负责 Wi-Fi、MQTT以及把数据提供给 Qt 6/C++ 上位机。双板之间使用带序号、ACK、超时和重传的串口协议，这样现场采集和网络连接可以解耦。
>
> 当前已经完成端到端实机验证。Qt 上位机一次实验显示温度23.8℃、湿度59.6%、风扇母线电压4.91V、电流168mA、功率825mW；这三个电量满足4.91乘0.168约等于0.825W。Modbus从站寄存器0和1分别是1234、5678，成功次数82、错误次数0，同时还能看到STM32心跳、ESP32 ACK和MQTT发布日志。
>
> 项目中最典型的问题是Modbus请求能到电脑从站，但STM32一开始读不到响应。电脑端能看到8字节请求，也能发出9字节正确响应，但OLED显示接收0/9字节和E3超时。因为0字节意味着问题还在返回链路或UART接收阶段，所以我没有先改CRC解析，也没有直接认定模块损坏。我把链路拆成电脑收请求、电脑发响应、A/B物理层、STM32 UART接收、协议校验五段，并在OLED增加实际接收字节数、原始十六进制数据和错误码。之后统一核对PA9、PA10、PB1方向控制、3.3V供电、共地、A/B以及从站的9600 8N1配置。最终OLED显示9/9 OK并解析出1234和5678，Qt端成功次数持续增加、错误为0。
>
> 另一个软件问题是MQTT首次连接早于Wi-Fi拿到IP。通过日志时间顺序，我确认Wi-Fi连接是异步的，于是把MQTT启动从顺序调用改成由GOT_IP事件触发。实机启动时先拿到IP，再启动MQTT，约630ms连接成功，不再出现首次DNS错误。
>
> 这个项目让我最大的收获不是把模块接起来，而是形成了分层排障习惯：先记录现象，区分事实和假设，再增加可观测信息逐段验证，最后用端到端数据闭环。下一步如果向产品化推进，我会增加示波器或逻辑分析仪波形证据、RS485隔离与保护、独立供电和PCB设计，并做长时间运行、断线重连和负载启动干扰测试。

## 七、常见追问与回答

### 1. 为什么使用 STM32 + ESP32，而不是只用 ESP32？

当前目标是把实时采集和网络侧解耦。STM32负责I2C、Modbus、OLED和确定性的周期任务，ESP32负责Wi-Fi、MQTT和上位机接口。网络断开或重连时不会阻塞现场采集。代价是硬件和双板协议更复杂；如果成本优先、实时要求较低，单ESP32也可以实现，我会根据产品约束取舍。

### 2. 为什么上 FreeRTOS？

项目同时有通信、传感器、Modbus、显示和健康监督等不同周期活动。FreeRTOS让任务职责、周期和故障范围更清楚，也便于后续增加队列、互斥、任务健康监控。它不是为了“显得高级”，如果功能很少、时序简单，裸机状态机同样可以完成。

### 3. `E3` 和 `B:0` 分别说明什么？

`E3` 是项目定义的响应头等待超时；`B:0` 或 `RX:0/9` 是本轮实际收到0字节。两者结合说明当时还没有进入完整帧的地址、功能码和CRC校验阶段。

### 4. 如何判断不是 CRC 算错？

失败现场实际接收字节数为0，CRC校验需要先拿到完整帧，因此CRC不是该阶段的首要矛盾。成功后收到完整9字节响应，并通过CRC和字段检查解析出1234、5678，证明解析链路可工作。

### 5. PB1 在 RS485 中做什么？

它控制半双工收发方向。发送请求前进入发送状态，UART发送完成后立即切回接收，否则可能错过从站快速返回的数据。具体高低电平要以所用模块的EN定义为准，不能脱离模块原理图死记。

### 6. 为什么RS485建议共地？

A/B是差分信号，但收发器仍有允许的共模范围。短距离非隔离实验中共地可以建立稳定参考，降低共模超范围导致的不稳定；工业现场则更适合使用隔离RS485、电源隔离和浪涌/ESD保护。

### 7. INA219没接风扇时为什么也可能显示电压？

未形成完整负载回路时，测量端可能浮空并受漏电、上拉和噪声影响，所以可能看到非零母线电压，但电流和功率接近0。传感器“I2C在线”只说明芯片能通信，不代表负载回路有效。接入风扇后，4.91V、168mA、825mW互相吻合，才是有效闭环。

### 8. Qt上位机为什么还需要串口日志？

上位机是面向使用者的结构化界面，原始串口日志是开发和故障定位证据。当前Qt程序既解析关键数据，也保留整理后的通信日志。产品运行时可以降低日志级别，但开发阶段不应完全删除可观测性。

### 9. 当前项目还有哪些局限？

- 仍是面包板样机，没有完成工业级PCB、隔离、EMC和环境认证。
- 当前Modbus实现以单从站、功能码03和低频轮询为主。
- UART接收仍有进一步升级为中断/DMA状态机的空间。
- 长时间运行和负载启动瞬态测试还需要更系统的数据和波形。
- Qt当前以监控为主；若要远程控制风扇，还需MOSFET/继电器驱动、命令确认、权限和失效安全策略。

## 八、面试表达中的边界

### 可以明确说“已经验证”

- STM32与ESP32心跳、匹配ACK、超时重传和复线恢复。
- AHT20、INA219、OLED实机采集显示。
- 电脑模拟Modbus从站，寄存器1234、5678端到端读取成功。
- ESP32连接Wi-Fi和MQTT并发布遥测与Modbus状态。
- Qt上位机实时显示完整数据，Modbus成功82次、错误0次的实验截图。
- MQTT改为获得IP后启动，并经实机日志验证。

### 只能说“计划改进”

- 工业级EMC、浪涌、ESD、隔离和认证。
- DMA版Modbus状态机。
- PCB与正式外壳。
- 大规模多从站轮询。
- 带执行器的远程闭环控制。
- 24小时以上全系统稳定性和负载瞬态波形测试（除非以后补做并记录）。

### 不建议这样说

- “RS485模块肯定坏了。”——当时没有形成器件级证据。
- “重新接线以后就莫名其妙好了。”——应说明你如何分段、观察了什么、最后如何验证。
- “这是工业级产品。”——当前更准确的说法是工业网关原型或面包板样机。
- “所有通信都用了DMA。”——当前实现不支持这个结论。
- “我做了完整故障诊断算法。”——现阶段主要是通信状态、错误计数、健康监控和远程可视化。
